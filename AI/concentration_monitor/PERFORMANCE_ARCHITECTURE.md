# 🚀 AI + WebRTC 아키텍처 및 성능 분석 리포트

## 1. 핵심 결론: "서버는 가볍게, 클라이언트는 바쁘게"
현재 개발하신 **Edge AI 방식(각자의 PC에서 Python이 분석)**은 6명 이상의 스터디룸 환경에서도 **서버 부하를 전혀 주지 않는 가장 효율적인 구조**입니다.

### 📡 데이터 전송량 비교 (서버 관점)
| 구분 | 내용 | 데이터 크기 | 부하 수준 |
| :--- | :--- | :--- | :--- |
| **WebRTC 영상** | 6명의 화상 채팅 (영상/음성) | 수백 MB ~ GB / 시간 | **매우 높음** (일반적인 화상회의 트래픽) |
| **AI 분석 데이터** | 집중도 점수, 상태 값 (JSON) | 수 KB / 시간 | **거의 없음** (카톡 메시지 수준) |

> **분석**: AI가 영상을 서버로 보내서 분석하는 것이 아니라, **각자의 컴퓨터에서 분석을 끝내고 "결과(집중함/딴짓함)"만 텍스트로 보내기 때문에**, 인원이 6명이든 60명이든  DB나 네트워크에는 아무런 무리가 가지 않습니다.

## 2. 주의해야 할 병목 구간 (Bottleneck)

### A. 클라이언트 PC의 CPU 과부하 🔥
서버 걱정은 없지만, 오히려 **사용자의 컴퓨터(Client PC)**가 힘들어할 수 있습니다.
*   **WebRTC**: 영상 인코딩/디코딩 (CPU/GPU 사용)
*   **AI (Python)**: 매 프레임 YOLO + MediaPipe 연산 (CPU/GPU 사용)
*   **위험**: 사양이 낮은 노트북에서는 팬이 심하게 돌거나 영상이 끊길 수 있습니다.
*   **해결책**:
    1.  `run.py`의 처리 속도를 조절 (예: 1초에 30번 분석 → 1초에 5번만 분석).
    2.  사람이 집중 상태를 0.1초 단위로 바꾸지 않으므로, **5fps 정도로 낮춰도 충분**합니다.

### B. 카메라 권한 충돌 (Critical) 📷
윈도우에서는 기본적으로 **하나의 카메라를 두 개의 프로그램이 동시에 쓸 수 없습니다.**
*   **시나리오**: 웹 브라우저가 스터디룸(WebRTC)을 위해 카메라를 켬 -> Python AI가 분석하려고 카메라를 켬 -> **에러 발생! (Access Denied)**
*   **해결책**:
    1.  **Virtual Camera (OBS 등)**: AI가 영상을 받아서 처리 후 '가상 카메라'로 송출 -> 브라우저가 이걸 입력으로 사용.
    2.  **Web 기반 AI 포팅**: Python 코드를 JavaScript(TensorFlow.js)로 변환하여 브라우저 내부에서 돌림. (가장 깔끔하지만 개발 공수 큼)
    3.  **플러그인 방식**: Electron 앱 등으로 감싸서 카메라 접근 제어.

## 3. "학습(Training)" 기능 추가에 대한 의견
> *"학습 기능을 넣으면 너무 무거워지지 않을까요?"*

**결론: 걱정하지 않으셔도 됩니다.**
제가 제안드린 **개인화 학습(SVM 등)**은:
1.  **타이밍**: 공부 시작 전 **딱 10초**만 수행합니다.
2.  **부하**: 엑셀 계산 수준이라 CPU를 거의 쓰지 않습니다.
3.  **실행 중(Runtime)**: 학습된 작은 수식 하나만 쓰기 때문에, YOLO보다 100배는 가볍습니다.

즉, **학습 기능을 넣는 것이 성능 저하의 원인이 되지는 않습니다.** (오히려 사용자에게 "AI가 나를 배우네?" 하는 좋은 경험을 줍니다.)

## 4. 최종 제언
현재 구조(Python 로컬 분석)를 유지하신다면:
1.  **카메라 충돌 문제**를 어떻게 풀 것인지가 가장 큰 기술적 과제입니다.
2.  **데이터 전송** 부분은 전혀 걱정 안 하셔도 됩니다. 매우 가볍습니다.
3.  **성능 튜닝**: `run.py` 분석 주기를 낮춰(`time.sleep`) 사용자의 PC 발열을 막아주는 것이 배려입니다.
